# ADR-0012: グローバル既定アロケータ ＋ 実行時フィールドによるオーバーライド（型引数にしない）

## Status
Accepted・未実装（計画）。[ADR-0011](0011-syscall-primitive-for-libc-independence.md)（libc 脱却）
の前提となるメモリ確保層の設計。現状 `Vec` は libc `malloc`/`free` を直呼びしている。

## Context
`Vec`（ヒープ）と将来の `Box`/`String` はメモリ確保を要する。今は codegen が `call @malloc` /
`free` を直に吐いている。libc 脱却（ADR-0011）に向けては確保層を差し替え可能にしたいが、
そのために **アロケータをどう表現し、どう差し込むか**を決める必要がある。

iris の核心は **所有権・機構を呼び出し側に露出しない**（ADR-0003）こと、トレイトは
**静的ディスパッチ・単相化**（ADR-0006）であること。Rust 流の `Vec<T, A: Allocator>`
（器にアロケータ型引数）は、ライフタイム注釈と同種の「機構の漏れ」で Go 的シンプルさに反する。

一方で「カスタムアロケータ（アリーナ等）を差し込みたい」要求はある。ここで本質的な制約:
**`free`/`realloc` は確保したのと同じアロケータで呼ばねば壊れる**（malloc で取ってアリーナへ
返す等は不正）。したがって「構築時にアロケータを差し込める」なら、その器は**どのアロケータで
確保したかを実行時に保持**せねばならず、その個体の `free`/`realloc` は動的ディスパッチになる。
「オーバーライドしたのにゼロコスト静的」は原理的に成立しない。

## Decision
**アロケータは `Allocator` トレイトとして表し、既定はグローバル単一アロケータ（静的・直呼び・
ゼロコスト）。オーバーライドは型引数ではなく、器に持たせた既定付きの実行時フィールドで行う。**

- トレイト（std）:

  ```iris
  trait Allocator {
      fn alloc(size: i64): RawPtr
      fn free(ptr: RawPtr, size: i64): void
      // realloc は Vec の grow 用に後で追加
  }
  type LibcAlloc = struct {}                       // 当面: libc を借りる実装
  impl Allocator for LibcAlloc { ... }             // 将来: MmapAlloc（mmap/munmap、ADR-0011）に差替
  ```

- **器の公開型はアロケータの有無に関わらず `Vec<T>`**（型シグネチャにアロケータを出さない＝
  ADR-0003 を満たす）。アロケータ性は**型ではなく実行時フィールド**で表す。`Vec` ヘッダを拡張:

  ```
  今:   Vec = { ptr, len, cap }
  案:   Vec = { ptr, len, cap, alloc }   // alloc == 0（センチネル）⇒ グローバル＝直呼び
  ```

- **既定構築**（`[1,2,3]` 等）は `alloc = 0`。codegen は `alloc == 0` を見て**グローバルへ直接
  確保/解放**を吐く（分岐1つで実質ゼロコスト）。**オーバーライド構築**（`Vec.with_alloc(a)`）は
  `a` を格納し、`free`/`realloc` はそれ経由（動的ディスパッチ）。
- 既存の Drop/free（`Vec` ローカルのスコープ末解放）は `alloc.free(ptr, size)` 経由に一段抽象化。
  **アリーナは `free` を no-op** にしてアリーナ自身の Drop で一括解放できる（個別解放の心配が消える）。
  `with_allocator(a) { ... }` のスコープ構文は、この「個体がハンドルを覚える」上の糖衣として後付け可。

**実装順**: ① `Allocator` トレイト ＋ `LibcAlloc`、**`Vec` ヘッダに `alloc` 追加（既定 0・挙動は
現状と同一）＝将来の seam** → ② `Vec.with_alloc`／アリーナ ＋ 借用検査の検証 → ③ `MmapAlloc` で
グローバル差替（libc malloc 消滅、ADR-0011 と接続）。

## Considered Options
- **型引数 `Vec<T, A>`（Rust 流）**: アリーナ等は素直だが、型引数 `A` が全所に漏れ ADR-0003 と衝突。却下。
- **既定 Vec は痩せ型・カスタムは別型**: 既定のメモリは据え置けるが、layout/codegen が 2 種に増え、
  公開型も分かれる。実装が重い。却下。
- **単一型・`Vec` ヘッダに常に `alloc` フィールド（採用）**: layout 一定で codegen が単純、公開型は
  `Vec<T>` 1 つ。代償は **Vec あたり +1 ワード**と free/realloc の **1 分岐**。実務でこの 1 ワードが
  問題になる場面はほぼ無いと判断。
- **アロケータを各ヒープオブジェクト自身に実装させる**: データと「メモリを配る」役が混ざり、全
  オブジェクトがアロケータ状態を抱えて太る。アロケータは「器」ではなく「配る人」に実装すべき。却下。

## Consequences
- 公開型を汚さずに「グローバル既定＋引数オーバーライド」が入る。既定経路は実質ゼロコスト、
  オーバーライドした個体のみ +1 分岐の動的ディスパッチ（コストは局所化）。
- `Vec` あたり +1 ワード（`alloc`）。`Box`/`String` も同様の seam を持たせると一貫する。
- **所有権 DAG との接続（要検証）**: 器がアロケータハンドルを持つ＝**`Vec` がアロケータを借用**する
  関係。アリーナは器より長生きせねばならず、これは ADR-0003 の自動ライフタイム推論（借用グラフ）で
  表現できる対象（アリーナがスコープを抜けるのに器が生きていれば借用検査が弾く想定）。ただし
  「ヒープ上の器が自分より長生きすべき借用を抱える」は現 `flow.rs`/`borrows.rs` で新パターンのため
  実装時に検証が要る。
- `Vec` の codegen の `malloc`/`free` 直呼びを「グローバルアロケータ呼び出し」へ一段抽象化することが、
  libc→mmap 差替（ADR-0011）を **Vec の codegen を触らずに**行うための肝になる。
