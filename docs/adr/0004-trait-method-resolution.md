# ADR-0004: メソッド名衝突は呼び出し側で `x.m#Qualifier()` により明示する

## Status
Accepted・実装済み（固有メソッド・trait 定義・`impl Trait for Type`・`#` 修飾子による解決と
曖昧性解消・固有 vs trait 同名の曖昧（D2）まで `tests/traits.rs` で縦断検証。記号衝突時は
固有 `@Type.method` / trait `@Type.Trait.method` を別記号で emit し `#` で振り分ける。
`for x#i32 in c` は `for` 未実装のため保留。）

## Context
trait を導入すると、ひとつの型が複数の trait を実装したときにメソッド名が衝突しうる。
解決の選択肢を検討した。

- Rust の UFCS（`Trait::method(x)` / `<T as Trait>::method()`）や `::` 区切りは iris の
  方針に合わない:
  - iris は呼び出しを**受け手先頭のドット記法** `x.m()` に統一している。
  - iris はパスもメンバも `.` で書く（`std.lib.foo`、`a.b`）。修飾にドットを使うと曖昧になる。
  - `::` は iris のどこにも存在しない記号で、ここだけ異物になる。
  - 「複雑さを呼び出し側に露出しない」が核心方針（ADR-0003）だが、**名前衝突だけは
    呼び出し側で解くしかない**性質のもの（同じ `x.m()` を 2 つの異なる実装へ向けられない）。
- 「同じ型は単一のメソッド集合を持つ」（Go 流）も検討したが、棄却した。理由:
  - 同名・同シグネチャでも**意味が違う**ことは普通にある（`Printable::len`＝文字数と
    `Buffer::len`＝バイト数がどちらも `(self): i32`）。シグネチャ一致を意味一致とみなして
    暗黙にひとつへマージするのは不健全。
  - よって衝突は**黙って解決せず、常に明示**させる方針を採る。

## Decision

### 修飾子構文 `x.m#Qualifier(args)`
名前が衝突するメソッドは、呼び出し側で `#` に続けて**提供元の名前**を書いて一意化する。

- `Qualifier` は **trait 名**（その trait が要求/提供する `m`）または **型名**（その型の
  固有メソッド `impl Type { ... }` の `m`）。`#名前` ＝「`m` を提供する名前空間」と読む。
- 例: 固有 `impl Point { fn at(self) }` と `impl Drawable for Point { fn at(self) }` が
  衝突するとき、`p.at#Point()`（固有）と `p.at#Drawable()`（trait）で指し分ける。
- `#` を**新しいトークン**として追加する（字句解析上、現在 `#` はどのトークンにも未使用）。
- `Qualifier` は**トレイトの型引数まで**含められる: `c.next#Iterator<i32>()`（ADR-0007 の
  複数 instantiation の曖昧解消）。`#` は一般の曖昧解消記号として、`for` の要素型にも及ぶ:
  `for x#i32 in c`。すなわち `#` は「呼び出し側で提供元を一意に絞る印」として言語横断で使う。

### 解決規則
呼び出し `x.m(...)`（修飾なし）:
1. `m` の提供元を集める = `x` の型の固有メソッド + `x` の型が実装する各 trait のうち
   `m` を持つもの。
2. **ちょうど 1 個** → そのまま解決（注釈ゼロ。衝突しない普通のメソッドは全部ここ）。
3. **0 個** → 「メソッド `m` はありません」エラー。
4. **2 個以上** → 曖昧エラー。提供元を列挙し `x.m#Qualifier()` で明示するよう促す。

呼び出し `x.m#Q(...)`（修飾あり）:
- `Q` が trait 名なら、その trait が `m` を持ち、かつ `x` の型がその trait を実装している
  ときに確定。`Q` が `x` の型名なら、その型の固有 `m` に確定。いずれも満たさなければエラー。

### 固有 vs trait の同名も曖昧扱い（D2）
固有メソッドと trait メソッドが同名のときも、固有を暗黙に優先しない。修飾なし `x.m()` は
**曖昧エラー**とし、`x.m#Point()`（固有）か `x.m#Trait()`（trait）の明示を要求する。
「衝突は隠さず常に明示」を一貫させるための選択（暗黙のシャドーイングを置かない）。

### 境界経由では修飾不要
ジェネリック境界の文脈では trait が一意に分かるため `#` は不要。

```
fn f<T: Printable>(x: T): string {
    return x.print()   // Printable::print に一意確定。# は書かない
}
```

`#` が要るのは、複数の提供元を持つ**具象値への直接呼び出し**だけ。

### 定義側の二重定義は従来どおりエラー
ひとつの `impl Type { ... }`（または同じ型への複数の固有 impl）に同名メソッドを 2 つ
置くのは単なる重複でありエラー（型検査で検出。実装済み）。同様に、ひとつの
`impl Trait for Type { ... }` 内の同名メソッドも重複エラー。衝突の明示が要るのは
**別々の提供元（固有/異なる trait）が同名を持つ**ときだけ。

## Consequences
- 呼び出しは常に受け手先頭のドット形 `x.m(...)` / `x.m#Q(...)` を保ち、`::` を導入しない。
  ADR-0003 の「呼び出し側に複雑さを出さない」を、衝突という不可避な一点に限って最小限の
  記法（`#Q`）で破る。
- 衝突しないメソッドは `x.m()` のまま（実用上の大多数）。`#` を書くのは本当に名前が
  ぶつかった具象呼び出しに限られる。
- D2 のため、固有と trait が同名なら直接呼び出しは必ず修飾が要る（やや冗長）が、
  取り違えは決して起きない。
- `#` は予約記号になる。将来この記号を他用途（属性など）へ使うことはできない。
- 本 ADR はメソッド**解決/曖昧性解消**のみを定める。trait の定義・`impl Trait for Type`・
  適合検査・デフォルト実装の機構は別途設計する。
